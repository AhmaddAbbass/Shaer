# 1. What Shaer Is

**Shaer** is an Arabic poetry platform built around a **specialized 7B poet model** (Shaer-7b-GRPO) and a bunch of support services + agents.

The goal is:

> A system where a user can talk in natural Arabic (“اكتب لي قصيدة عن…”, “صلّح هذا البيت…”, “هات قصيدة للحماسة…”) and an **agentic backend** decides:
>
> * what data to retrieve,
> * what specs to infer (meter, era, poet style, description),
> * which model to call,
> * how to evaluate/repair the outputs,
> * and finally returns a clean, on-meter poem or a curated set of existing poems.

There’s **no UI yet**. We’re designing everything from **models → microservices → agents**, so that later you can plug in any frontend.

# 2. Core Ingredients

## 2.1 Models

We have several ML models in play:

1. **Yehia-7B (Navid-AI/Yehia-7B-preview)**

   * General Arabic LLaMA-style model.
   * Good at expressive Arabic prose, some poetry, reasoning.
   * Used as:

     * **Spec-builder**: turn a user’s messy request into a clean structured poem spec.
     * **Poetry critic**: give feedback on generated bayts.
     * **Explainer**: explain/annotate poems for users.

2. **Shaer-7b-GRPO**

   * Your fine-tuned poet model.
   * Base: Yehia-7B.
   * Trained with SFT on verse-level instruction data:

     * Input: an Arabic prompt describing meter, era, poet, description, previous verses, instructions.
     * Output: **one bayt** (صدر + عجز on a single line).
   * It is **not** a chat model in the wild; it expects a very specific prompt template.

3. **Scansion (meter) model(s)**

   * “Ashaar” models that take a bayt and a target meter and judge if the bayt matches that meter.
   * Output:

     * `meter_score` (0–100),
     * `on_meter` bool,
     * `notes` (short Arabic explanation).

4. **Optional classifiers** (not fully wired yet but conceptually present)

   * Theme / era / style classifiers for poems.
   * Useful for analysis, filtering, and auto-detecting attributes for user-provided poems.

---

## 2.2 Data & RAG

You have a full **poetry knowledge graph + vector index**:

1. **Poem-level dataset** (`Shaer-AI/ashaar-full-desc-preprocessed`)

   Each poem row has:

   * poem_title, poem_meter, poem_theme, poem_url
   * poet_name, poet_era, poet_location
   * poem_language_type, num_verses, poem_id
   * **poem_description**: an Arabic prose summary generated by Yehia
   * cleaning flags (`has_bad_description`, `needs_resummarization`)

2. **RAG stack (RAG/ folder)**

   * **Neo4j graph** with nodes:

     * `Poem`, `Poet`, `Era`, `Meter`, `Theme`, `SourceSite`.
   * Relationships like: `(:Poem)-[:WRITTEN_BY]->(:Poet)`, `(:Poem)-[:OF_METER]->(:Meter)`, etc.
   * **Chroma vector store**:

     * Embeddings of cleaned `poem_description` for semantic search.
     * Only “good” descriptions (not placeholders, not verse copies).

3. **RAG pipeline** (`shaer_rag`)

   * `dataset.py`, `cleaning.py`, `graph.py`, `vector.py`, `pipeline.py`.
   * CLI:

     * `build_pipeline.py` → load HF, clean, fill Neo4j, build Chroma.
     * `query_chroma.py` → semantic search against Chroma.

This is the **memory bank** that user queries will tap into for inspiration, retrieval, and specs.

# 3. Backend Services (Microservice Layer)

Under `services/` you have several independent services, each with its own API and Dockerfile.

All services share **one schemas file**:

### 3.1 `services/common_schemas/`

* `schemas.py` – defines the basic objects everyone uses:

  * **`PoemSpec`**
    Structured description of the poem we want to generate:

    * `poem_title` (optional)
    * `poem_meter` (required: e.g. "البسيط")
    * `poem_theme` (optional: "غزل", "رثاء", ...)
    * `poem_era` (optional: "العصر العباسي", "العصر الحديث", ...)
    * `poet_name` (optional)
    * `poem_description` (required prose summary, Ashaar-style)
    * `num_verses` (int, how many bayts to generate)

  * **`Verse`**

    * `text`: full bayt as “صدر … عجز” in one line.
    * `index`: bayt index (1-based) in the poem.

  * **`Poem`**

    * `spec`: `PoemSpec`
    * `verses`: list[`Verse`]
    * `metadata`: optional `poem_id`, `source_url`, etc.

  * **`BaytMeterEval`**

    * `target_meter`: meter we expected.
    * `meter_score`: int (0–100).
    * `on_meter`: bool.
    * `notes`: short Arabic text.

  * **`YehiaFeedback`**

    * `ok`: bool (acceptable bayt or not).
    * `score`: int (0–100, optional).
    * `feedback`: Arabic explanation what is good/bad and how to improve.

  * **RAG types**:

    * `RagSearchRequest`: `{query_text, top_k}`
    * `RagSearchHit`: one candidate poem summary.
    * `RagSearchResponse`: list of hits.
    * `RagPoemRecord`: full poem with verses + metadata.

  * **`LLMMessage`**: `{role, content}` for chat-style calls.

Everyone imports these types, so field names and shapes are consistent across services.

## 3.2 Shaer Client Service (`services/shaer_client/`)

**Purpose:**
“Make Shaer talk” safely. It is the only service that knows exactly how Shaer was trained and how to talk to it.

### What it exposes

* `POST /generate-bayt`

  * Input: `{ spec: PoemSpec, previous_verses: [Verse], sequence_number: int }`
  * Output: `{ verse: Verse }`

* (Optional) `POST /generate-poem`

  * Input: `{ spec: PoemSpec }`
  * Internal: loops over `generate-bayt` from 1..num_verses.
  * Output: `{ poem: Poem }`

### What it does internally

* Builds the **exact `messages` array** Shaer expects (system+user) using `app/prompt.py`:

  ```text
  [ 
    { "role": "system", "content": "أنت شاعر عربي متمكن..." },
    { "role": "user", "content": "المطلوب منك في هذه المهمة أن تولّد بيتًا..." }
  ]
  ```

  The user content includes:

  * `- البحر: {spec.poem_meter}`
  * `- الوصف العام لموضوع القصيدة: {spec.poem_description}`
  * `- العصر: {spec.poem_era}` (or general wording if missing)
  * `- الشاعر: {spec.poet_name}` (or “أسلوب عام”)
  * `- عدد أبيات القصيدة الكلي: {spec.num_verses}`
  * `- ترتيب البيت المطلوب داخل القصيدة: {sequence_number}`
  * “الأبيات السابقة في القصيدة:” followed by either:

    * “لا توجد أبيات سابقة…” for the first bayt, or
    * numbered list of previous bayts.
  * “إرشادات مهمة:” – fixed bullet points telling Shaer:

    * produce exactly one bayt,
    * one line (صدر + عجز),
    * correct meter,
    * no explanations/titles.

* Sends these `messages` to the **RunPod Shaer endpoint** (`client.py`), which applies the chat template and returns the generated bayt.

It is responsible for **never breaking the training prompt structure**.

## 3.3 Yehia Client Service (`services/yehia_client/`)

**Purpose:**
Wrap Yehia and give higher-level endpoints:

* generic chat,
* building `PoemSpec` from user requests (+ RAG context),
* giving feedback on individual bayts.

### Endpoints

* `POST /chat`

  * Input: `messages: list[LLMMessage]`
  * Output: `text: str`

* `POST /build-spec`

  * Input: `{ user_query: str, rag_hits?: list[RagSearchHit] }`
  * Output: `{ spec: PoemSpec }`

* `POST /feedback`

  * Input: `{ verse_text: str, spec: PoemSpec }`
  * Output: `{ feedback: YehiaFeedback }`

### Internals

* `app/prompt.py` holds Yehia prompts:

  * Spec-building system message:
    “أنت مخطط قصائد عربي، وظيفتك تحويل طلب المستخدم إلى مواصفات قصيدة (بحر، موضوع، عصر، شاعر، وصف، عدد أبيات)…”
  * Feedback system message:
    “أنت ناقد شعري، تقيم بيتًا واحدًا بناءً على مواصفات القصيدة…”

* `build_spec_messages(user_query, rag_hits)`:

  * Presents the user query plus some top retrieved poem descriptions/meters/themes from RAG.
  * Asks Yehia to return a structured spec (or a pseudo-JSON that the service parses into `PoemSpec`).

* `build_feedback_messages(verse_text, spec)`:

  * Scaffolds a prompt where Yehia reads spec + verse and outputs judgment + suggestions.

This service is your **semantic reasoning layer**: it translates fuzzy human intent into a structured `PoemSpec`, and critiques semantics/style of bayts.

---

## 3.4 RAG Service (`services/rag_service/`)

**Purpose:**
HTTP API over your Neo4j + Chroma stack.

### Endpoints

* `GET /search?text=...&top_k=5`

  * Uses Chroma semantic search over poem descriptions.
  * Returns `RagSearchResponse`.

* `GET /poem/{poem_id}`

  * Uses Neo4j to fetch full poem text + metadata.
  * Returns `RagPoemRecord`.

* `GET /filter?poet_name=&meter=&era=&theme=&limit=`

  * Uses Neo4j filters to retrieve poems by metadata.

* (Optional) `GET /similar/{poem_id}`

  * Combines graph neighbors + vector similarity to suggest related poems.

### Internals

* `neo4j_client.py`:

  * Handles connections and Cypher queries.
  * Responsible for consistent mapping of Neo4j records → `RagPoemRecord`.

* `chroma_client.py`:

  * Handles semantic search calls.
  * Respects `CHROMA_MODE` (HTTP vs local persistent).

This service is the **library**: everything about retrieving, ranking, and inspecting **existing** poems goes through here.

---

## 3.5 Meter Services (`services/meter_service/` + `services/ashaar_meter_service/`)

**Purpose:**
Provide bayt-level feedback via two focused services:

1. `meter_service`: wraps the BiLSTM classifier (keras/tf) to score whether a bayt matches a target meter (`BaytMeterEval` response).
2. `ashaar_meter_service`: wraps Ashaar's structural analysis to report similarity scores (0–1) for any bayt irrespective of the classifier.

### Endpoint

* `meter_service`: `POST /eval-bayt`

  * Input: `{ verse_text: str, target_meter: str }`
  * Output: `{ result: BaytMeterEval }`

* `ashaar_meter_service`: `POST /ashaar-score`

  * Input: `{ verse_text: str }`
  * Output: `{ score: float, notes: str }`

### Internals

* `meter_service/app/scansion.py`:

  * Wraps the underlying scansion model(s).
  * Interprets the model’s raw outputs.
  * Converts them into:

    * `meter_score` (0–100),
    * `on_meter` (bool, based on some threshold),
    * `notes`.

* `ashaar_meter_service/app/ashaar.py`:

  * Wraps Ashaar’s `BaitAnalysis`.
  * Normalizes `[sep]` verses and calls `ashaar_meter_pattern_score`.
  * Returns normalized float scores and short notes.

Together these services tell the **Enhancer agent** whether to regenerate a bayt and how far it drifted structurally.

# 4. Agentic Layer (Orchestrator + sub-agents)

On top of HTTP services, you’ll have an **orchestrator LLM** (e.g., ChatGPT running with MCP tools) that is the *only thing the user talks to*.

It sees tools like:

* `yehia_client.build_spec`
* `yehia_client.feedback`
* `shaer_client.generate_bayt`
* `rag_service.search`, `rag_service.poem`, `rag_service.filter`
* `meter_service.eval_bayt`

And uses them in **multi-step workflows**.

Conceptually you have these **agent roles** (even if they’re not separate physical services):

1. **Orchestrator Agent**

   * Receives the raw user query in Arabic.
   * Detects intent (“generate new poem”, “fix my poem”, “search by topic”, “search by poet”, “explain poem”, etc.).
   * Chooses which tools to call and in what order.
   * If the intent is unclear, asks the user clarifying questions through Yehia if needed.

2. **Spec Builder Agent** (implemented via `yehia_client` + `rag_service`)

   * When the user wants a **new poem**:

     * Calls `rag_service.search` with the user query.
     * Feeds top `RagSearchHit`s + `user_query` to `yehia_client.build_spec`.
     * Gets back a `PoemSpec` that is:

       * consistent with user intent,
       * filled with plausible meter/theme/era/poet,
       * described in the Ashaar prose style.

3. **Generation Agent** (via `shaer_client` and maybe `meter_service`)

   * Takes `PoemSpec`.
   * For each bayt index from 1 to `spec.num_verses`:

     * Calls `shaer_client.generate_bayt` with `spec`, `previous_verses`, `sequence_number`.
     * Optionally calls `meter_service.eval_bayt` and `yehia_client.feedback`.
     * Accepts or regenerates the bayt based on scores.
   * Returns the final `Poem`.

4. **Critic/Enhancer Agent**

   * Operating bayt-by-bayt:

     * Given a generated or user-provided bayt, it:

      * calls `meter_service.eval_bayt` (meter check),
       * calls `yehia_client.feedback` (semantic/style check).
     * Decides:

       * if `on_meter=False` or `feedback.ok=False` → ask `shaer_client` to regenerate this bayt (with maybe slightly tweaked instructions such as “ركز أكثر على كذا…”) but same general prompt skeleton.
   * This feedback loop continues until:

     * meter is OK, and
     * Yehia’s feedback is OK,
     * or a retry limit is reached (e.g., 3 attempts per bayt).

5. **Library Agent** (via `rag_service`)

   * Handles queries where the user wants **existing poems**:

     * “هات قصيدة عن الشوق في العصر العباسي”
     * “أريد قصيدة للمتنبي في الحماسة”
   * Uses:

     * `rag_service.search` (topic),
     * `rag_service.filter` (metadata filters),
     * Then maybe `rag_service.poem/{id}` to get full text.
   * The orchestrator then returns these poems to the user, possibly with Yehia explanations.

# 5. Main User Stories & How They Flow Through the System

### 5.1 User Story A – “Generate me a new poem about X”

Example:

> “اكتب لي قصيدة من ثمانية أبيات عن شوق المغترب إلى وطنه، بأسلوب حديث قريب من نزار قباني.”

**Flow:**

1. **User → Orchestrator**
   Orchestrator LLM sees intent = *“generate new poem”*.

2. **Spec building**

   * Orchestrator calls `rag_service.search` with query `"قصيدة عن شوق المغترب إلى وطنه"`, `top_k=5`.
   * It passes the hits + original query to `yehia_client.build_spec`.
   * Yehia returns:

     ```text
     PoemSpec(
       poem_meter="الكامل",
       poem_theme="غزل/حنين",
       poem_era="العصر الحديث",
       poet_name="أسلوب قريب من نزار قباني",
       poem_description="قصيدة تعبر عن شوق المغترب لوطنه وأهله...",
       num_verses=8
     )
     ```

3. **Generation loop (bayt by bayt)**
   For each `i` from 1 to 8:

   * Orchestrator calls `shaer_client.generate_bayt` with:

     * `spec` from above,
     * `previous_verses` = bayts 1..(i-1),
     * `sequence_number = i`.
   * Shaer returns `verse_i`.

4. **Meter + semantic check per bayt**
   For each bayt:

  * Orchestrator calls `meter_service.eval_bayt` with `verse_i.text`, `spec.poem_meter`.
   * Orchestrator may call `yehia_client.feedback` with `verse_i.text`, `spec`.
   * If either:

     * `on_meter == False`, or
     * `feedback.ok == False`,

     it calls `shaer_client.generate_bayt` again (maybe with slightly stricter “إرشادات مهمة” through `prompt.py`), limited by some `WORKFLOW_MAX_BAYT_RETRIES`.

5. **Return to user**

   * Once all bayts are generated and accepted, the orchestrator returns:

     * The full poem text (lines 1..8).
     * Optionally:

       * short explanation of the poem’s theme,
       * meter name,
       * maybe links to similar classical poems (via `rag_service`).

---

### 5.2 User Story B – “Fix my poem”

Example:

> “هذا البيت مكسور، صححه لي من فضلك:
> *يا قلبُ لا تعشقِ الدنيا وزينتها*”

**Flow:**

1. User sends the bayt (or whole poem) to the orchestrator with a “fix” intent.

2. Orchestrator either:

   * **Infers a spec** for the poem using `yehia_client.build-spec` (on the whole poem or the user description).
  * Or asks `yehia_client.feedback` + `meter_service.eval_bayt` on each bayt to identify which ones are broken.

3. For each problematic bayt:

  * call `meter_service.eval_bayt` → see meter issues.
   * call `yehia_client.feedback` → get textual critique.

4. Then the orchestrator uses `shaer_client.generate_bayt` to **regenerate only the broken bayts**:

   * It keeps `PoemSpec` fixed (same meter, description, style).
   * It includes the **neighboring bayts as previous_verses** so Shaer respects context.
   * It loops until the new bayt passes meter + Yehia feedback (or hits retry limit).

5. Orchestrator returns the **repaired poem** to the user, optionally with an explanation of what changed and why.

---

### 5.3 User Story C – “Give me poems about a topic”

Example:

> “أعطني ثلاث قصائد عن الصبر في العصر العباسي.”

**Flow:**

1. Orchestrator sees retrieval intent.

2. It calls `rag_service.search` with query `"قصيدة عن الصبر في العصر العباسي"`, `top_k` large (say 20).

3. Optionally:

   * Passes the hits through Yehia (`/chat`) to pick the top 3 that best match nuance.

4. For each selected hit:

   * Calls `rag_service.poem/{poem_id}` to get full poem and URL.

5. Orchestrator returns:

   * Short card for each poem: title, poet, meter, description.
   * Full text (or at least first few bayts).
   * Link to source (poem_url).

---

### 5.4 User Story D – “Give me a poem from poet X”

Example:

> “أريد قصيدة حماسية للمتنبي.”

**Flow:**

1. Orchestrator calls `rag_service.filter` with `poet_name="المتنبي"`, maybe `theme="حماسة"`, plus limit.

2. It chooses one or several poems from hits.

3. Calls `rag_service.poem/{id}` for full text.

4. Returns the poem(s) to the user.

---

### 5.5 User Story E – “Explain/Analyze this poem”

Example:

> “اشرح لي هذا البيت:
> *إذا غامَرْتَ في شَرَفٍ مَرُومِ*…”

**Flow:**

1. Orchestrator sees analysis intent.

2. Calls `yehia_client.chat` or a dedicated `/explain-poem` endpoint that:

   * uses a system message like “اشرح البيت بأسلوب مبسط…”
   * optionally uses RAG to find the poem + context.

3. Returns explanation to user (maybe with bullet points, vocabulary, meter mention, etc.).

# 6. How It All Ties Together Technically

* **Models** live on **Hugging Face** and are served via **RunPod serverless**:

  * `Yehia-7B` serverless endpoint.
  * `Shaer-7b-GRPO` serverless endpoint.

* **RAG stack**: `RAG/docker-compose` spins up:

  * Neo4j,
  * Chroma,
  * plus your `build_pipeline.py` to ingest from HF.

* **Services layer** (`services/`):

  * `yehia_client`, `shaer_client`, `rag_service`, `meter_service`.
  * Each has its own Dockerfile and **can run independently**.
  * A root `docker-compose.yml` will run them together and wire ports.

* **Agentic layer**:

  * Orchestrator LLM (e.g., ChatGPT with MCP tools) sees these services as tools.
  * It implements all workflows by calling the right HTTP endpoints in the right order based on the user query and intermediate results.

This makes the system:

* **Modular**: you can swap the meter model, change the RAG index, or fine-tune Shaer-7B again without rewriting the orchestrator.
* **Inspectable**: each step is a clear API call with typed inputs/outputs.
* **Agentic**: the orchestrator can reason about failures (e.g., low meter score) and try different strategies (regenerate, adjust spec, etc.) until a threshold is reached.
